Executive Summary

Problem

MySQL 8.x instances can encounter temporary tablespace issues when the InnoDB temporary tablespace (e.g., the ibtmp1 file) grows excessively or fills up. This is usually triggered by heavy query workloads (large sorts, aggregations, joins, etc.) that spill to disk, leading to disk space exhaustion, performance degradation, or even query failures (ERROR 1114 – The table is full). In Cloud SQL, this manifests as rapid growth of "Tmp_data" usage, potentially consuming all available storage. Cloud SQL's auto-storage increase may expand disk size to accommodate growth, but temporary space is not freed until a MySQL restart, leaving the instance with permanently higher storage utilization (and cost) unless addressed.
Key Root Causes

Almost any operation that cannot be completed in memory may spill to the temp tablespace. Common culprits include complex queries (large JOINs, GROUP BY, ORDER BY, DISTINCT, heavy CTEs/subqueries, window functions, etc.) that create massive internal temporary tables. Unoptimized queries (e.g., missing indexes, selecting excessive rows/columns) often cause MySQL to sort or group using disk-based temp files. InnoDB always uses the ibtmp1 file for on-disk temp tables in MySQL 8, and this file never shrinks during runtime. Concurrent large temp tables or long-running temp operations can accumulate and quickly exhaust disk space. Other factors include insufficient memory (causing more operations to spill to disk), misconfiguration of temp limits, or even InnoDB purge lag (delayed cleanup of undo logs for temp tables) that bloats the temp tablespace. In Cloud SQL, the lack of OS-level access means DBAs must rely on MySQL's instrumentation and Cloud Monitoring to detect these issues.
Impact

Symptoms range from performance slowdowns (due to heavy disk I/O for temp files) and storage bloat (Cloud SQL auto-increasing disk size due to ibtmp1 growth), to query failures ("table full" errors) or even instance unavailability if disk fills completely. A replica may experience replication lag if a heavy temp-table-using query is replayed serially, and session leaks (connections left open with large CREATE TEMPORARY TABLE data) can hold temp space indefinitely. Because Cloud SQL does not allow shrinking storage, prevention and timely resolution are critical.
Solution Approach

This playbook provides a step-by-step workflow to diagnose, troubleshoot, and resolve MySQL temp tablespace issues on GCP Cloud SQL. It guides DBAs to quickly identify offending queries (using Performance Schema, Cloud SQL logs, etc.), assess temp space usage (e.g., via INFORMATION_SCHEMA.FILES for innodb_temporary), and take immediate remedial actions (such as killing runaway sessions, enabling emergency storage auto-grow, or restarting if needed). Then it delves into root cause analysis and permanent fixes, optimizing queries (adding indexes, rewriting queries, using optimizer hints), adjusting MySQL configuration parameters (e.g., increasing tmp_table_size if appropriate, tuning buffer sizes), and addressing Cloud SQL-specific constraints (like using flags for config changes, managing read replicas and failovers). The playbook also covers monitoring and alerting setup (Cloud Monitoring metrics, log-based alerts for temp space usage) and preventative best practices to avoid recurrence (query design guidelines, periodic reviews, capacity planning).
Expected Outcomes

By following this playbook, the team will be able to:
Diagnose temp space issues in minutes
Pinpoint the root-cause query within 30 minutes
Apply safe immediate mitigations (e.g., kill or throttle the offending workload) within 10 minutes
Implement long-term optimizations within a day
The goal is not only to resolve the current incident but to establish ongoing monitoring and safeguards so that MySQL temp space issues are caught early or prevented entirely.

Root Cause Analysis – Understanding Temporary Tablespace Issues {#root-cause-analysis}

Temporary tablespace problems in MySQL 8 are almost always symptoms of underlying query or configuration issues. This section explores all potential root causes of temp tablespace growth or errors, ensuring no stone is left unturned.
1. Heavy Queries Creating Large Temporary Tables

MySQL creates implicit temporary tables for certain SQL operations. If these result sets are large, they can consume significant space:
Sorting and Grouping Operations

Queries with expensive ORDER BY, GROUP BY, or DISTINCT clauses often use a temp table to sort or deduplicate results. The execution proceeds in two phases: MySQL first gathers results into a temp table, then sorts or groups them. Large datasets here mean a large temp table on disk.
Joins and Unindexed Searches

Joining large tables without proper indexes (or SELECTs with broad LIKE '%...%' filters) can prevent efficient indexed lookup. MySQL may resort to scanning and storing intermediate results in a temp table (especially for hash joins or if using block nested loop with a large buffer). Unoptimized joins thus contribute to temp usage.
UNIONs, Derived Tables, and CTEs

UNION (especially UNION DISTINCT) combines results via a temp table unless certain conditions allow streaming. Derived tables (subqueries in the FROM clause) and Common Table Expressions (WITH) are often materialized into temp tables for the optimizer to treat as tables. MySQL 8 sometimes can optimize away materialization, but complex CTEs usually materialize, consuming temp space.
Large Aggregations

Computing aggregates (SUM, COUNT(DISTINCT ...), etc.) on large unindexed columns may create temp tables. Functions like GROUP_CONCAT() and COUNT(DISTINCT) explicitly use temp tables if memory is insufficient.
Window Functions

MySQL 8 window functions (e.g., ranking functions) often need to buffer partitions of data. The optimizer will use temp tables as needed for windowing steps. Large window function result sets = large temp usage.
Multiple-table UPDATE/DELETE

Complex updates joining tables or subqueries may create internal temp tables for intermediate results (e.g., for the SELECT part of an UPDATE ... JOIN).
INSERT … SELECT on same table

In MySQL, inserting into a table from a subquery on the same table uses a temp table to store the select output before insertion.
Why this causes issues: If these operations produce more data than fits in memory, MySQL will spill to disk (the temp tablespace). For example, any result needing sorting that doesn't fit in the sort_buffer_size will be written to a temp file on disk (filesort algorithm). Similarly, huge intermediate results (hundreds of MB or more) will exceed the in-memory temp table threshold and convert to on-disk tables. On Cloud SQL, all such disk spills ultimately write to the ibtmp1 file (since MySQL 8 uses InnoDB for disk temp storage), causing ibtmp1 to balloon.
Supporting facts: MySQL's manual confirms a temp table is needed for many of the above situations. If the temp table is small it stays in memory, but beyond a threshold it goes to disk. The default limit for in-memory temp tables is 16 MB (controlled by tmp_table_size and max_heap_table_size). Queries involving TEXT/BLOB columns automatically use disk-based temps, no matter how small, due to engine limitations.
2. Disk Space Exhaustion & ibtmp1 Growth Patterns

The InnoDB temporary tablespace (ibtmp1) is a single file (or set of files) on disk used for all on-disk temp tables. Key characteristics that can lead to problems:
No Auto-Shrink

The ibtmp1 file grows as needed but does not shrink until MySQL restarts. Even after temp tables are dropped and space is internally freed for reuse, the file remains at its high-water mark size. This means repeated large temp usages can ratchet up the file size over time.
Reuse vs. Release

Although space within ibtmp1 can be reused by new temp tables (so the server won't infinite-loop allocate space once the file is large), it won't release space back to the OS. If free disk is low, this can eventually lead to "disk full" errors even if no single query is using that entire space at once.
Autoextend & Cloud SQL Auto-Resize

By default, ibtmp1 is autoextending (e.g., starts at 12MB and grows). On Cloud SQL, if automatic storage increase is enabled, the underlying disk will expand when usage approaches capacity. A burst of temp space usage can trigger multiple auto-resizes, permanently increasing your allocated storage (since Cloud SQL cannot shrink disks). If auto-resize is off or hits its limit, the instance will error out (data disk is full in logs).
Write I/O Overhead

As ibtmp1 grows, writing/reading those large temp tables imposes heavy disk I/O. If the storage is not very fast or if the instance hits IOPS limits, overall query throughput suffers. This can manifest as slow queries or high I/O wait on the instance.
Example scenario: Consider a workload with periodic heavy analytical queries. The first time a 5 GB temp table is created, ibtmp1 grows to ~5 GB. If later another query needs 8 GB, ibtmp1 grows to 8 GB. Even after those queries finish, ibtmp1 stays at 8 GB. If multiple concurrent queries each use ~8 GB, the file may grow to ~(8 GB × number of concurrent queries) before reuse kicks in, because each session's temp table is separate. It's easy to see how disk can be exhausted by a burst of temp activity.
Cloud SQL implications: Because you cannot manually shrink ibtmp1 on Cloud SQL (no OS access, and MySQL has no shrink command), the only way to reset ibtmp1 is to restart the instance. This frees the space internally and if autogrow had occurred, leaves you with a lot of free space on disk (but you're still paying for that storage unless you contact support to reduce it). Frequent uncontrolled growth indicates you should identify the offending query patterns and either limit them or plan for enough disk headroom.
3. Runaway Temporary Tables & Memory Spillover

"Runaway" temporary table usage refers to scenarios where temp space grows uncontrollably due to one or more sessions:
Implicit Temp Table Spillover

MySQL tries to use memory for temp tables first (using the TempTable engine by default in 8.0). If an internal temp table exceeds tmp_table_size (and max_heap_table_size for user memory tables), it is converted to an on-disk temp table. Similarly, if the total memory used by temp tables across threads exceeds certain limits (temptable_max_ram, etc.), MySQL may start writing to disk. In MySQL 8, by default temptable_max_ram is 1 GB or 3% of server memory (whichever is larger, capped at 4 GB). If this is exceeded (and memory-mapped files are disabled by default), MySQL will use disk (InnoDB temp files) for new temp table allocations. A workload that triggers this (lots of concurrent temp table usage or one huge operation) can suddenly cause a flood of disk temp data.
Sort Buffer and Join Buffer Exhaustion

MySQL uses per-session memory buffers for sort and join operations (sort_buffer_size, join_buffer_size). If data to sort exceeds sort_buffer_size, MySQL performs a disk-based merge sort (creating temp files for sorted runs) – effectively another kind of temp file usage. Similarly, insufficient join buffer can force MySQL to repeatedly scan/join in pieces, possibly writing temp state to disk. Enlarging these buffers can reduce disk I/O per query, but be cautious: they are allocated per thread, so setting them too large can exhaust RAM if many threads do sorting/joining concurrently.
Unbounded Intermediate Results

A poorly constrained query (e.g., missing a WHERE clause or an extremely large DISTINCT) can create a temp table of enormous size unintentionally. If such a query runs for a long time, it might fill up the temp space (especially if multiple such queries run). Example: a SELECT DISTINCT on a column of a 100-million-row table without an index will force sorting all 100 million values. If each value is, say, 100 bytes, that's ~10 GB of data that might go into a temp table on disk.
Symptoms: During such "runaway" events, you may see MySQL processlist entries in states like "Copying to tmp table" or "Copying to tmp table on disk" for extended durations. The Cloud SQL monitoring would show tmp_data climbing continuously. Eventually, errors like "The table '#sqlXXX' is full" or "No space left on device" may appear when queries cannot allocate more temp space.
4. Configuration Issues and Mis-tuned Parameters

Several MySQL configuration variables directly control temp table behavior. Misconfiguration or default settings not suited for your workload can contribute to problems:
tmp_table_size and max_heap_table_size

These define the max size of an in-memory temp table (the lesser of the two applies per temp table). If set too low (default ~16MB), even moderately sized intermediate results will spill to disk. If set too high relative to available RAM and workload, you risk memory exhaustion if many large temp tables stay in RAM concurrently. The balance must be based on workload – e.g., OLAP queries might benefit from a higher limit to avoid disk I/O, whereas OLTP with many concurrent small temp tables might keep defaults.
internal_tmp_mem_storage_engine

In MySQL 8, the default is TempTable (a new engine optimized for varchars, supports large blobs in memory up to limits). The alternative is MEMORY (the old engine, which pads VARCHARs and doesn't allow large BLOB/TEXT). Sticking with TempTable is generally best for performance, but there have been bugs (e.g., early MySQL 8 versions had issues that made switching to MEMORY a temporary workaround). In Cloud SQL 8.x, you would rarely change this – only consider if you suspect a specific bug with TempTable engine.
temptable_max_ram / temptable_max_mmap

These global limits cap memory usage of the TempTable engine. By default, temptable_max_ram is 1 GB (minimum) and temptable_max_mmap=0 (meaning MySQL will not use memory-mapped temp files by default). If you have plenty of RAM, increasing temptable_max_ram can allow more/larger temp tables to stay in memory (reducing disk usage). Enabling memory-mapped files (by setting a nonzero temptable_max_mmap) could let MySQL use temp files that are deleted on close (thus not persisting like ibtmp1), but note that Cloud SQL's tmpdir is on a non-accessible path; plus, the default is disabled to avoid uncontrolled use of file system space.
innodb_temp_data_file_path

This defines initial size and autoextend settings for ibtmp1. In Cloud SQL, you cannot easily change this (and it likely uses the default "ibtmp1:12M:autoextend"). In regular MySQL, one might set a maximum size (max: size) to prevent infinite growth, but this simply causes queries to error out once the cap is hit. On Cloud SQL, setting such a cap is not advisable, better to rely on monitoring and auto-resize to avoid a crash, then fix the underlying issue.
performance_schema and sys schema settings

Although not a direct cause of temp usage, Performance Schema collects a lot of data in memory and can itself be resource-intensive if fully enabled. Some performance_schema queries (especially those joining large history tables) might create temp tables to produce reports. If you've increased Performance Schema instrumentation (e.g., statement history size), that could indirectly create larger temp tables when querying the data. By default, though, the overhead is modest.
Cloud SQL constraints: Configuration changes on Cloud SQL are done via flags in the UI or gcloud command (no my.cnf to edit). Some flags (like tmp_table_size) can be set dynamically, others might require a restart (the Cloud SQL docs or interface will indicate if a flag change needs reboot). Also, Cloud SQL might restrict certain flags for compatibility – always verify the flag is allowed.
5. Performance Schema Instrumentation Overhead

This is a less common cause, but worth noting for completeness: if Performance Schema and the MySQL sys schema (which provides handy views) are heavily used, they could contribute to temp usage:
Many of the sys schema views (like sys.statements_with_temp_tables) run queries on Performance Schema tables, aggregating data. Those aggregation queries themselves might create internal temp tables (especially if the Performance Schema summary tables contain many rows due to a high number of normalized query patterns).
If you enable full query digest collection and have thousands of different query patterns, the Performance Schema summary tables (e.g., events_statements_summary_by_digest) could grow large (hundreds or thousands of rows). Selecting from them with ordering could use a temp table for sorting results.
However, this is typically not a primary driver of persistent temp tablespace growth because these tables are memory-resident and any temp table used to format a result is short-lived.
In summary, the Performance Schema is unlikely to fill your disk, but if you are aggressively querying it during heavy load, it could be a small piece of the puzzle. Ensure Performance Schema is configured appropriately (perhaps limit history sizes, etc.) so it doesn't become an additional burden during an incident.
6. Connection/Session Leaks Holding Temp Resources

MySQL user-created temporary tables (created with CREATE TEMPORARY TABLE) exist per session and are dropped automatically when the session ends. If an application opens a temp table and either forgets to drop it or the session remains open (idle or leaked in a connection pool), that temp table's data remains in the temp tablespace:
Long-lived temp tables

For example, if a user session created a temp table and inserted 1 GB of data into it, ibtmp1 will have grown (since by default a user temp table will use InnoDB and thus ibtmp1 for its data and undo logs). If the session is left open (perhaps an app connection that didn't close), that 1 GB stays allocated. Even if the table is not actively used, MySQL cannot reclaim that space until the table is dropped or the session ends.
Abandoned sessions

In Cloud SQL, if your connection pool does not properly close connections, or an interactive session (e.g., a MySQL client shell) is left running with a temp table open, you have a "leak." MySQL's wait_timeout might eventually close truly idle sessions, but many frameworks execute periodic keep-alive queries to keep connections open. Check that wait_timeout on Cloud SQL is reasonable (the default might be 10 minutes, but some Cloud SQL setups use higher timeouts).
Open transactions holding undo

Slightly different angle, if a session had a long-running open transaction that involved changes to a temporary table (or even a normal table), the undo for those changes can't be purged until commit. For user temp tables, those undo logs reside in ibtmp1 as well. A "stuck" transaction could thus bloat temp space with pending undo. This is rare but possible (e.g., a transaction that created a temp table, did large inserts/deletes, and never committed/rolled back because the app hung).
Detection: Use SHOW PROCESSLIST or Performance Schema (events_statements_current, etc.) to see if there are threads with some "Opening tables" or just sleeping but user is known to create temp tables. You can also query INFORMATION_SCHEMA.INNODB_TEMP_TABLE_INFO, it lists user-created temp tables that currently exist (with the session ID that owns them). If that table is huge, that's a smoking gun. In Cloud SQL, this table should be accessible; it will show the table name (which is something like #sql..., unless the app named it explicitly) and creation time.
Resolution: Identify the session (by Id or user/host from INNODB_TEMP_TABLE_INFO or processlist) and terminate it if it's not needed. Killing the session will drop all its temp tables and free the space (though ibtmp1 won't shrink, it will just mark it free internally). In the long term, fix the application logic to ensure temp tables are dropped and connections are not leaked (consider lowering wait_timeout or using connection pooler settings to aggressively recycle idle connections).
7. Replication and Temp Tables (Lag/Failover Considerations)

If you use Cloud SQL read replicas or external replicas, replication can surface unique issues with temp tables:
Statement-based replication and temp tables

If the primary uses statement-based binlog format (rare in Cloud SQL, which defaults to ROW format), temp tables can cause inconsistencies. Statements involving temp tables do not replicate well – e.g., a CREATE TEMPORARY TABLE ... SELECT ... on primary will execute fine, but the replica may not have the same temp table context if it restarts, etc. Thankfully, Cloud SQL uses row-based replication by default, avoiding this pitfall.
Row-based replication lag due to heavy queries

Even with row-based replication, if the primary runs a huge query that creates a massive temp table, the replica has to perform the same work (the actual data inserted into the temp table might be written via row events, or the entire operation might be contained in a transaction to apply). If that query was slow on primary, it could be slow on replica too, causing replica lag.
Failover impact

In a High Availability configuration (Primary-Replica), if a temp-space issue on primary causes a failover (e.g., primary restarts due to error or you manually fail over to relieve pressure), the new primary (which was the replica) might not have the same temp tables. However, since temp tables are session-bound, on failover those are lost. This generally clears the problem (since a restart is involved), but any in-flight transactions that used temp tables are aborted. After failover, ibtmp1 on the new primary will be empty (fresh process), which is good – but ensure the root cause (query) doesn't just run again and trigger the same issue.
Mitigation:
Offload heavy queries to replicas or analytics servers when possible
If using multiple parallel workers (slave_parallel_workers), be aware that frequent use of temp tables in transactions can limit parallelism
Ensure the replica has autoresize on as well, so it can handle temp growth
Test failover scenarios if you rely on them for clearing issues
8. InnoDB Temporary Tablespace Mechanism (MySQL 8 Specifics)

Since this playbook focuses on MySQL 8, it's important to note how MySQL 8's temp tablespace works compared to older versions:
Engine = InnoDB only

Location

By default ibtmp1 resides in the data directory. You can configure innodb_temp_data_file_path to place it elsewhere (relative to datadir). Cloud SQL does not allow changing datadir or using custom paths, so essentially ibtmp1 lives on the same disk as your data. This means heavy temp usage contends with regular data for disk bandwidth and space.
Reset on restart

On clean shutdown, MySQL will remove ibtmp1. On startup it recreates a fresh 12MB file. This is why restart is a "solution" to reclaim space – it starts fresh (but again, Cloud SQL disk size won't shrink automatically).
Temporary table undo logs

In MySQL 8, undo logs for changes to user-created temporary tables are stored in ibtmp1 (since they're not durable and shouldn't pollute the main undo logs). If a workload does large updates on temp tables within a transaction, that can generate lots of undo in ibtmp1. Normally purge will remove it once transaction commits, but if purge is lagging behind, ibtmp1 might keep growing. This is part of the earlier "purge lag" cause – essentially, check if Innodb_history_list_length (length of undo log list) is huge and not coming down; that could hint that purge isn't keeping up, possibly due to large temp table churn.
By understanding all these causes, we can better target our troubleshooting. Next, we focus on detecting the specific queries and processes that are driving temp space usage.
Identifying Problematic Queries (Critical Focus)



The single most important task in resolving temp tablespace issues is finding which queries or operations are consuming the space. This section provides an in-depth guide to detecting high temp-space queries and analyzing them for optimization.
Detecting High Temp Table Usage Queries

MySQL 8 provides performance metrics that make it easier to find offending queries:
1. Performance Schema (Statement Digests)

The events_statements_summary_by_digest table aggregates statistics per normalized query pattern. It has counters for how many temp tables each query generated:
SUM_CREATED_TMP_TABLES – total temp tables (memory + disk) created by that query across all executions
SUM_CREATED_TMP_DISK_TABLES – how many of those were disk-based temp tables
Script 1: Top 10 Query Patterns by Disk Temp Tables



SELECT 
    DIGEST_TEXT AS query_pattern,
    COUNT_STAR AS exec_count,
    SUM_CREATED_TMP_TABLES AS total_temp_tables,
    SUM_CREATED_TMP_DISK_TABLES AS disk_temp_tables,
    ROUND(SUM_CREATED_TMP_DISK_TABLES / NULLIF(SUM_CREATED_TMP_TABLES, 0) * 100, 1) AS pct_temp_on_disk,
    ROUND(AVG_TIMER_WAIT / 1000000000000, 2) AS avg_exec_time_sec,
    ROUND(SUM_SORT_ROWS / COUNT_STAR, 0) AS avg_rows_sorted
FROM performance_schema.events_statements_summary_by_digest
WHERE SUM_CREATED_TMP_TABLES > 0
ORDER BY SUM_CREATED_TMP_DISK_TABLES DESC
LIMIT 10;
This will show queries that often spill to disk. A high pct_temp_on_disk (near 100%) means the query's temp results rarely fit in memory.
Script 2: Queries with High Temp Table Usage per Execution



SELECT 
    DIGEST_TEXT AS query_pattern,
    COUNT_STAR AS exec_count,
    ROUND(SUM_CREATED_TMP_DISK_TABLES / COUNT_STAR, 2) AS avg_disk_temps_per_exec,
    ROUND(SUM_CREATED_TMP_TABLES / COUNT_STAR, 2) AS avg_total_temps_per_exec,
    ROUND(AVG_TIMER_WAIT / 1000000000000, 2) AS avg_exec_time_sec,
    FIRST_SEEN,
    LAST_SEEN
FROM performance_schema.events_statements_summary_by_digest
WHERE SUM_CREATED_TMP_TABLES > 0
  AND COUNT_STAR > 0
ORDER BY avg_disk_temps_per_exec DESC
LIMIT 10;
This identifies queries that consistently create many disk temp tables per execution, even if not run frequently.
2. sys.statements_with_temp_tables View

Cloud SQL includes the MySQL "sys" schema by default, which has convenient views on Performance Schema.
Script 3: Using sys Schema for Temp Table Analysis



SELECT 
    query,
    db,
    exec_count,
    total_latency,
    memory_tmp_tables,
    disk_tmp_tables,
    ROUND((disk_tmp_tables / NULLIF(memory_tmp_tables, 0)) * 100, 1) AS pct_disk,
    avg_tmp_tables_per_exec,
    tmp_tables_to_disk_pct,
    first_seen,
    last_seen
FROM sys.statements_with_temp_tables 
WHERE disk_tmp_tables > 0
ORDER BY disk_tmp_tables DESC 
LIMIT 15;
3. Current Running Queries (Processlist)

If the temp space issue is happening right now, inspect active queries.
Script 4: Find Currently Executing Queries Using Temp Tables



SELECT 
    p.ID,
    p.USER,
    p.HOST,
    p.DB,
    p.COMMAND,
    p.TIME AS duration_sec,
    p.STATE,
    LEFT(p.INFO, 200) AS query_snippet,
    CONCAT(t.PROCESSLIST_USER, '@', t.PROCESSLIST_HOST) AS full_user,
    t.THREAD_ID,
    s.SQL_TEXT
FROM INFORMATION_SCHEMA.PROCESSLIST p
JOIN performance_schema.threads t ON t.PROCESSLIST_ID = p.ID
LEFT JOIN performance_schema.events_statements_current s ON s.THREAD_ID = t.THREAD_ID
WHERE p.STATE LIKE '%tmp table%' 
   OR p.STATE LIKE '%Sorting%'
   OR p.STATE LIKE '%filesort%'
   OR p.STATE LIKE '%Creating sort index%'
ORDER BY p.TIME DESC;
Script 5: Long-Running Queries (Potential Temp Table Culprits)



SELECT 
    ID,
    USER,
    HOST,
    DB,
    COMMAND,
    TIME AS duration_sec,
    STATE,
    LEFT(INFO, 300) AS query_text
FROM INFORMATION_SCHEMA.PROCESSLIST
WHERE COMMAND != 'Sleep'
  AND TIME > 30  -- Running for more than 30 seconds
ORDER BY TIME DESC
LIMIT 20;
4. Temp Table Usage by Session

Script 6: Identify Which Sessions Are Creating Most Temp Tables



SELECT 
    t.THREAD_ID,
    t.PROCESSLIST_ID,
    t.PROCESSLIST_USER,
    t.PROCESSLIST_HOST,
    t.PROCESSLIST_DB,
    t.PROCESSLIST_STATE,
    COUNT(esh.EVENT_ID) AS statement_count,
    SUM(esh.CREATED_TMP_TABLES) AS total_tmp_tables,
    SUM(esh.CREATED_TMP_DISK_TABLES) AS total_disk_tmp_tables,
    ROUND(SUM(esh.CREATED_TMP_DISK_TABLES) / NULLIF(SUM(esh.CREATED_TMP_TABLES), 0) * 100, 1) AS pct_disk
FROM performance_schema.threads t
LEFT JOIN performance_schema.events_statements_history esh ON esh.THREAD_ID = t.THREAD_ID
WHERE t.PROCESSLIST_ID IS NOT NULL
GROUP BY t.THREAD_ID
HAVING total_tmp_tables > 0
ORDER BY total_disk_tmp_tables DESC
LIMIT 20;
5. User-Created Temporary Tables (Session Leaks)

Script 7: Find All Active User-Created Temporary Tables



SELECT 
    temp.NAME AS table_name,
    temp.SPACE AS tablespace_id,
    temp.PER_TABLE_TABLESPACE,
    temp.ROW_FORMAT,
    t.THREAD_ID,
    t.PROCESSLIST_ID,
    t.PROCESSLIST_USER,
    t.PROCESSLIST_HOST,
    t.PROCESSLIST_DB,
    t.PROCESSLIST_TIME AS session_duration_sec,
    t.PROCESSLIST_STATE,
    t.PROCESSLIST_INFO
FROM INFORMATION_SCHEMA.INNODB_TEMP_TABLE_INFO temp
JOIN performance_schema.threads t ON t.THREAD_ID = temp.SPACE  -- Note: mapping may vary
ORDER BY temp.SPACE;
Note: The exact mapping between INNODB_TEMP_TABLE_INFO and session info may require joining on appropriate columns based on your MySQL version.

7. Memory Usage by TempTable Engine

Script 9: Check TempTable Engine Memory Usage



SELECT 
    EVENT_NAME,
    CURRENT_COUNT_USED AS objects_in_use,
    CURRENT_NUMBER_OF_BYTES_USED / 1024 / 1024 AS current_mb,
    HIGH_COUNT_USED AS high_objects,
    HIGH_NUMBER_OF_BYTES_USED / 1024 / 1024 AS high_watermark_mb,
    LOW_COUNT_USED,
    LOW_NUMBER_OF_BYTES_USED / 1024 / 1024 AS low_mb
FROM performance_schema.memory_summary_global_by_event_name 
WHERE EVENT_NAME LIKE 'memory/temptable/%'
ORDER BY CURRENT_NUMBER_OF_BYTES_USED DESC;
This shows how much memory the TempTable engine is currently using and its high-water mark.
Analyzing and Optimizing the Culprit Queries

After identifying problematic query patterns, perform a deep analysis:
EXPLAIN the Query

Script 10: Comprehensive EXPLAIN Analysis



-- Run EXPLAIN in JSON format for detailed analysis
EXPLAIN FORMAT=JSON
SELECT ...your query here...;
-- Or use traditional format
EXPLAIN 
SELECT ...your query here...;
-- For MySQL 8.0.18+, use EXPLAIN ANALYZE for actual execution stats
EXPLAIN ANALYZE
SELECT ...your query here...;
Look for these indicators in EXPLAIN output:
"Using temporary" in Extra column indicates temp table usage
"Using filesort" indicates disk-based sorting
"type: ALL" indicates full table scan (often requires temp tables)

Example Optimizations

Example 1: SELECT DISTINCT with ORDER BY

Problem Query:



SELECT DISTINCT customer_id 
FROM orders 
ORDER BY order_date DESC;
Issues:
MySQL collects all 50M orders
Sorts by date
Then removes duplicates
Creates huge temp table
Optimized Solution:



SELECT customer_id, MAX(order_date) AS last_order_date 
FROM orders 
GROUP BY customer_id 
ORDER BY last_order_date DESC;
Required Index:



CREATE INDEX idx_customer_orderdate ON orders(customer_id, order_date);
Example 2: JOIN without Index and Large GROUP BY

Problem Query:



SELECT u.country, COUNT(l.log_id) AS log_count
FROM users u
JOIN logs l ON u.user_id = l.user_id
GROUP BY u.country;
Issues:
No index on logs.user_id
No index on users.country
Full table scan and massive temp table
Solution:



-- Add necessary indexes
CREATE INDEX idx_logs_userid ON logs(user_id);
CREATE INDEX idx_users_country ON users(country);
-- Alternative: Pre-aggregate approach
SELECT u.country, SUM(log_counts.cnt) AS log_count
FROM users u
JOIN (
    SELECT user_id, COUNT(*) AS cnt
    FROM logs
    GROUP BY user_id
) AS log_counts ON u.user_id = log_counts.user_id
GROUP BY u.country;
Example 3: Large CTE Materialization

Problem Query:



WITH large_cte AS (
    SELECT complex_calculation(...)
    FROM huge_table
    WHERE date_range = last_year  -- Returns 5M rows
)
SELECT *
FROM large_cte
JOIN other_table ON ...
WHERE specific_condition = 'X';  -- Filters down to 1000 rows
Solution:



-- Push filter into CTE or use derived table instead
SELECT *
FROM (
    SELECT complex_calculation(...)
    FROM huge_table
    WHERE date_range = last_year
      AND some_column IN (
          SELECT related_column 
          FROM other_table 
          WHERE specific_condition = 'X'
      )
) AS derived
JOIN other_table ON ...;
-- Or use temporary table with index
CREATE TEMPORARY TABLE temp_results (
    INDEX idx_join_col (join_column)
) AS
SELECT complex_calculation(...)
FROM huge_table
WHERE date_range = last_year
  AND specific_condition = 'X';
SELECT * FROM temp_results JOIN other_table ON ...;
DROP TEMPORARY TABLE temp_results;

CREATE TEMPORARY TABLE kill_candidates AS
SELECT 
    p.ID,
    p.USER,
    p.HOST,
    p.DB,
    p.COMMAND,
    p.TIME AS duration_sec,
    p.STATE,
    LEFT(p.INFO, 200) AS query_snippet,
    COALESCE(trx.trx_rows_modified, 0) AS rows_modified,
    COALESCE(trx.trx_rows_locked, 0) AS rows_locked,
    CASE 
        WHEN p.STATE LIKE '%tmp table%' AND p.TIME > 600 THEN 10  -- High priority
        WHEN p.STATE LIKE '%Sorting%' AND p.TIME > 300 THEN 9
        WHEN p.TIME > 1800 THEN 8
        WHEN esc.CREATED_TMP_DISK_TABLES > 5 THEN 7
        WHEN trx.trx_rows_locked > 10000 THEN 6
        ELSE 5
    END AS kill_priority,
    CASE 
        WHEN trx.trx_rows_modified > 0 THEN 'CAUTION: Has modified data'
        WHEN trx.trx_rows_locked > 1000 THEN 'CAUTION: Holds many locks'
        WHEN p.USER = 'replication_user' THEN 'CRITICAL: Do not kill replication'
        WHEN p.COMMAND = 'Binlog Dump' THEN 'CRITICAL: Do not kill binlog thread'
        ELSE 'Safe to kill'
    END AS risk_assessment,
    CONCAT('KILL ', p.ID, ';') AS kill_command
FROM INFORMATION_SCHEMA.PROCESSLIST p
LEFT JOIN INFORMATION_SCHEMA.INNODB_TRX trx ON trx.trx_mysql_thread_id = p.ID
LEFT JOIN performance_schema.events_statements_current esc 
    ON esc.THREAD_ID = (SELECT THREAD_ID FROM performance_schema.threads WHERE PROCESSLIST_ID = p.ID)
WHERE p.COMMAND != 'Sleep'
  AND p.USER NOT IN ('event_scheduler', 'system user')
  AND (
    p.STATE LIKE '%tmp table%'
    OR p.STATE LIKE '%Sorting%'
    OR p.TIME > 300
    OR esc.CREATED_TMP_DISK_TABLES > 0
  )
ORDER BY kill_priority DESC, duration_sec DESC;
-- Review the candidates
SELECT * FROM kill_candidates;
-- Execute kills for high-priority, safe candidates
SELECT kill_command 
FROM kill_candidates 
WHERE kill_priority >= 8 
  AND risk_assessment = 'Safe to kill';

WITH query_analysis AS (
    SELECT

        COUNT(DISTINCT COLUMN_NAME) AS column_count

    LEFT JOIN INFORMATION_SCHEMA.COLUMNS c USING (TABLE_SCHEMA, TABLE_NAME)
    WHERE TABLE_SCHEMA NOT IN ('mysql', 'information_schema', 'performance_schema', 'sys')

)

#!/usr/bin/env python3
"""
Push MySQL temp tablespace metrics to Cloud Monitoring
Requires: google-cloud-monitoring, mysql-connector-python
"""
from google.cloud import monitoring_v3
import mysql.connector
import time
from datetime import datetime
PROJECT_ID = "YOUR_PROJECT_ID"
INSTANCE_CONNECTION = "YOUR_CONNECTION_NAME"
DB_USER = "root"
DB_PASS = "YOUR_PASSWORD"
def get_temp_usage(cursor):
    """Get temporary tablespace usage percentage"""
    query = """
    SELECT ROUND(
        ((TOTAL_EXTENTS - FREE_EXTENTS) / TOTAL_EXTENTS * 100), 2
    ) AS pct_used
    FROM INFORMATION_SCHEMA.FILES 
    WHERE TABLESPACE_NAME='innodb_temporary'
    """
    cursor.execute(query)
    result = cursor.fetchone()
    return float(result[0]) if result else 0.0
def get_disk_temp_rate(cursor):
    """Calculate disk temp tables creation rate"""
    query = "SHOW GLOBAL STATUS LIKE 'Created_tmp_disk_tables'"
    cursor.execute(query)
    result = cursor.fetchone()
    return int(result[1]) if result else 0
def write_metric(client, project_name, metric_type, value):
    """Write time series data to Cloud Monitoring"""
    series = monitoring_v3.TimeSeries()
    series.metric.type = f"custom.googleapis.com/mysql/{metric_type}"
    series.resource.type = "global"
    now = time.time()
    seconds = int(now)
    nanos = int((now - seconds) * 10 ** 9)
    interval = monitoring_v3.TimeInterval(
        {"end_time": {"seconds": seconds, "nanos": nanos}}
    )
    point = monitoring_v3.Point(
        {"interval": interval, "value": {"double_value": value}}
    )
    series.points = [point]
    client.create_time_series(name=project_name, time_series=[series])
def main():
    # Connect to MySQL
    conn = mysql.connector.connect(
        unix_socket=f"/cloudsql/{INSTANCE_CONNECTION}",
        user=DB_USER,
        password=DB_PASS
    )
    cursor = conn.cursor()
    # Setup Cloud Monitoring client
    client = monitoring_v3.MetricServiceClient()
    project_name = f"projects/{PROJECT_ID}"
    # Store initial value for rate calculation
    prev_disk_temps = get_disk_temp_rate(cursor)
    prev_time = time.time()
    try:
        while True:
            # Get metrics
            temp_usage = get_temp_usage(cursor)
            current_disk_temps = get_disk_temp_rate(cursor)
            current_time = time.time()
            # Calculate rate (tables per minute)
            time_diff = (current_time - prev_time) / 60  # in minutes
            disk_temp_rate = (current_disk_temps - prev_disk_temps) / time_diff if time_diff > 0 else 0
            # Write to Cloud Monitoring
            write_metric(client, project_name, "temp_tablespace_usage_pct", temp_usage)
            write_metric(client, project_name, "disk_temp_tables_rate", disk_temp_rate)
            print(f"[{datetime.now()}] Temp Usage: {temp_usage}%, Disk Temp Rate: {disk_temp_rate:.2f}/min")
            # Update previous values
            prev_disk_temps = current_disk_temps
            prev_time = current_time
            # Wait 60 seconds before next measurement
            time.sleep(60)
    except KeyboardInterrupt:
        print("\nMonitoring stopped")
    finally:
        cursor.close()
        conn.close()
if __name__ == "__main__":
    main()

#!/bin/bash
# Real-time monitoring of temp tablespace usage
# Runs in terminal, updates every 5 seconds
CONNECTION_NAME="YOUR_CONNECTION_NAME"
REFRESH_INTERVAL=5
clear
while true; do
    tput cup 0 0  # Move cursor to top-left
    echo "=== MySQL Temporary Tablespace Monitor ==="
    echo "Timestamp: $(date)"
    echo "Refresh: ${REFRESH_INTERVAL}s | Press Ctrl+C to exit"
    echo ""
    mysql -h /cloudsql/$CONNECTION_NAME -u root -p <<EOF
-- Temp tablespace usage
SELECT 
    'Temp Tablespace' AS metric,
    CONCAT(ROUND((TOTAL_EXTENTS - FREE_EXTENTS) * @@innodb_page_size / 1024 / 1024, 2), ' MB') AS used,
    CONCAT(ROUND(TOTAL_EXTENTS * @@innodb_page_size / 1024 / 1024, 2), ' MB') AS total,
    CONCAT(ROUND(((TOTAL_EXTENTS - FREE_EXTENTS) / TOTAL_EXTENTS * 100), 2), '%') AS pct_used
FROM INFORMATION_SCHEMA.FILES 
WHERE TABLESPACE_NAME='innodb_temporary'
UNION ALL
-- Temp table statistics
SELECT 
    'Disk Temp Tables',
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME='Created_tmp_disk_tables'),
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME='Created_tmp_tables'),
    CONCAT(ROUND((
        (SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME='Created_tmp_disk_tables') /
        NULLIF((SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME='Created_tmp_tables'), 0)
    ) * 100, 2), '%');
-- Active sessions using temp
SELECT '\n--- Active Temp Operations ---' AS '';
SELECT 
    ID,
    USER,
    LEFT(HOST, 20) AS host,
    TIME AS duration_sec,
    LEFT(STATE, 30) AS state,
    LEFT(INFO, 80) AS query
FROM INFORMATION_SCHEMA.PROCESSLIST
WHERE STATE LIKE '%tmp%' OR STATE LIKE '%Sorting%'
ORDER BY TIME DESC
LIMIT 5;
-- Top temp table users
SELECT '\n--- Top 5 Query Patterns by Disk Temp Usage ---' AS '';
SELECT 
    COUNT_STAR AS execs,
    SUM_CREATED_TMP_DISK_TABLES AS disk_temps,
    ROUND(AVG_TIMER_WAIT/1000000000000, 2) AS avg_sec,
    LEFT(DIGEST_TEXT, 100) AS query
FROM performance_schema.events_statements_summary_by_digest
WHERE SUM_CREATED_TMP_DISK_TABLES > 0
ORDER BY SUM_CREATED_TMP_DISK_TABLES DESC
LIMIT 5;
EOF
    sleep $REFRESH_INTERVAL
done
Script 48: Temp Usage Trend Analysis



-- Historical trend analysis of temp table usage
-- Run this daily to track patterns
CREATE TABLE IF NOT EXISTS temp_usage_history (
    measurement_time DATETIME NOT NULL,
    tmp_tables_total BIGINT,
    tmp_disk_tables_total BIGINT,
    disk_temp_pct DECIMAL(5,2),
    ibtmp1_size_mb DECIMAL(10,2),
    ibtmp1_used_mb DECIMAL(10,2),
    top_query_digest VARCHAR(64),
    top_query_disk_temps BIGINT,
    PRIMARY KEY (measurement_time)
) ENGINE=InnoDB;
-- Insert current snapshot
INSERT INTO temp_usage_history
SELECT 
    NOW() AS measurement_time,
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
     WHERE VARIABLE_NAME='Created_tmp_tables') AS tmp_tables_total,
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
     WHERE VARIABLE_NAME='Created_tmp_disk_tables') AS tmp_disk_tables_total,
    ROUND((
        (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
         WHERE VARIABLE_NAME='Created_tmp_disk_tables') /
        NULLIF((SELECT VARIABLE_VALUE FROM performance_schema.global_status 
                WHERE VARIABLE_NAME='Created_tmp_tables'), 0)
    ) * 100, 2) AS disk_temp_pct,
    (SELECT ROUND(TOTAL_EXTENTS * @@innodb_page_size / 1024 / 1024, 2)
     FROM INFORMATION_SCHEMA.FILES 
     WHERE TABLESPACE_NAME='innodb_temporary') AS ibtmp1_size_mb,
    (SELECT ROUND((TOTAL_EXTENTS - FREE_EXTENTS) * @@innodb_page_size / 1024 / 1024, 2)
     FROM INFORMATION_SCHEMA.FILES 
     WHERE TABLESPACE_NAME='innodb_temporary') AS ibtmp1_used_mb,
    (SELECT DIGEST FROM performance_schema.events_statements_summary_by_digest 
     WHERE SUM_CREATED_TMP_DISK_TABLES > 0 
     ORDER BY SUM_CREATED_TMP_DISK_TABLES DESC LIMIT 1) AS top_query_digest,
    (SELECT SUM_CREATED_TMP_DISK_TABLES FROM performance_schema.events_statements_summary_by_digest 
     WHERE SUM_CREATED_TMP_DISK_TABLES > 0 
     ORDER BY SUM_CREATED_TMP_DISK_TABLES DESC LIMIT 1) AS top_query_disk_temps;
-- View trends (last 7 days)
SELECT 
    DATE(measurement_time) AS date,
    MAX(disk_temp_pct) AS max_disk_temp_pct,
    AVG(disk_temp_pct) AS avg_disk_temp_pct,
    MAX(ibtmp1_size_mb) AS max_ibtmp1_size_mb,
    MAX(ibtmp1_used_mb) AS max_ibtmp1_used_mb,
    COUNT(*) AS measurements
FROM temp_usage_history
WHERE measurement_time >= DATE_SUB(NOW(), INTERVAL 7 DAY)
GROUP BY DATE(measurement_time)
ORDER BY date DESC;
-- Identify concerning trends
SELECT 
    'TREND ANALYSIS' AS analysis_type,
    CASE 
        WHEN (SELECT MAX(disk_temp_pct) FROM temp_usage_history 
              WHERE measurement_time >= DATE_SUB(NOW(), INTERVAL 7 DAY)) > 50
        THEN 'WARNING: High disk temp percentage detected'
        WHEN (SELECT MAX(ibtmp1_size_mb) FROM temp_usage_history 
              WHERE measurement_time >= DATE_SUB(NOW(), INTERVAL 7 DAY)) > 
             (SELECT AVG(ibtmp1_size_mb) FROM temp_usage_history 
              WHERE measurement_time >= DATE_SUB(NOW(), INTERVAL 30 DAY)) * 1.5
        THEN 'WARNING: ibtmp1 size increased significantly'
        ELSE 'OK: Temp usage within expected parameters'
    END AS assessment;

-- Generate daily performance report
-- Schedule this to run daily and email results
DELIMITER //
CREATE PROCEDURE generate_daily_temp_report()
BEGIN
    DECLARE report_date DATE;
    SET report_date = CURDATE();
    -- Create temporary reporting table
    CREATE TEMPORARY TABLE IF NOT EXISTS daily_report (
        section VARCHAR(100),
        metric VARCHAR(100),
        value VARCHAR(500),
        severity ENUM('INFO', 'WARNING', 'CRITICAL')
    );
    -- Section 1: Overall Statistics
    INSERT INTO daily_report
    SELECT 
        'Overall Statistics' AS section,
        'Total Temp Tables Created' AS metric,
        (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
         WHERE VARIABLE_NAME='Created_tmp_tables') AS value,
        'INFO' AS severity
    UNION ALL
    SELECT 
        'Overall Statistics',
        'Disk Temp Tables Created',
        (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
         WHERE VARIABLE_NAME='Created_tmp_disk_tables'),
        CASE 
            WHEN (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
                  WHERE VARIABLE_NAME='Created_tmp_disk_tables') > 1000000
            THEN 'WARNING'
            ELSE 'INFO'
        END
    UNION ALL
    SELECT 
        'Overall Statistics',
        'Disk Temp Percentage',
        CONCAT(ROUND((
            (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
             WHERE VARIABLE_NAME='Created_tmp_disk_tables') /
            NULLIF((SELECT VARIABLE_VALUE FROM performance_schema.global_status 
                    WHERE VARIABLE_NAME='Created_tmp_tables'), 0)
        ) * 100, 2), '%'),
        CASE 
            WHEN ROUND((
                (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
                 WHERE VARIABLE_NAME='Created_tmp_disk_tables') /
                NULLIF((SELECT VARIABLE_VALUE FROM performance_schema.global_status 
                        WHERE VARIABLE_NAME='Created_tmp_tables'), 0)
            ) * 100, 2) > 50
            THEN 'CRITICAL'
            WHEN ROUND((
                (SELECT VARIABLE_VALUE FROM performance_schema.global_status 
                 WHERE VARIABLE_NAME='Created_tmp_disk_tables') /
                NULLIF((SELECT VARIABLE_VALUE FROM performance_schema.global_status 
                        WHERE VARIABLE_NAME='Created_tmp_tables'), 0)
            ) * 100, 2) > 20
            THEN 'WARNING'
            ELSE 'INFO'
        END;
    -- Section 2: Top Offending Queries
    INSERT INTO daily_report
    SELECT 
        'Top Offenders',
        CONCAT('Query #', @rownum := @rownum + 1),
        CONCAT(
            'Digest: ', LEFT(DIGEST, 16), ' | ',
            'Disk Temps: ', SUM_CREATED_TMP_DISK_TABLES, ' | ',
            'Executions: ', COUNT_STAR, ' | ',
            'Avg Time: ', ROUND(AVG_TIMER_WAIT/1000000000000, 2), 's'
        ),
        CASE 
            WHEN SUM_CREATED_TMP_DISK_TABLES > 10000 THEN 'CRITICAL'
            WHEN SUM_CREATED_TMP_DISK_TABLES > 1000 THEN 'WARNING'
            ELSE 'INFO'
        END
    FROM performance_schema.events_statements_summary_by_digest, (SELECT @rownum := 0) r
    WHERE SUM_CREATED_TMP_DISK_TABLES > 0
    ORDER BY SUM_CREATED_TMP_DISK_TABLES DESC
    LIMIT 10;
    -- Section 3: Resource Usage
    INSERT INTO daily_report
    SELECT 
        'Resource Usage',
        'Temp Tablespace Size',
        CONCAT(
            ROUND(TOTAL_EXTENTS * @@innodb_page_size / 1024 / 1024, 2), ' MB total, ',
            ROUND((TOTAL_EXTENTS - FREE_EXTENTS) * @@innodb_page_size / 1024 / 1024, 2), ' MB used (',
            ROUND(((TOTAL_EXTENTS - FREE_EXTENTS) / TOTAL_EXTENTS * 100), 2), '%)'
        ),
        CASE 
            WHEN ROUND(((TOTAL_EXTENTS - FREE_EXTENTS) / TOTAL_EXTENTS * 100), 2) > 80
            THEN 'CRITICAL'
            WHEN ROUND(((TOTAL_EXTENTS - FREE_EXTENTS) / TOTAL_EXTENTS * 100), 2) > 60
            THEN 'WARNING'
            ELSE 'INFO'
        END
    FROM INFORMATION_SCHEMA.FILES 
    WHERE TABLESPACE_NAME='innodb_temporary';
    -- Section 4: Recommendations
    INSERT INTO daily_report
    SELECT 
        'Recommendations',
        'Action Required',
        CASE 
            WHEN COUNT(*) > 0 THEN 'Review and optimize queries with high disk temp usage'
            ELSE 'No immediate action required'
        END,
        CASE 
            WHEN COUNT(*) > 0 THEN 'WARNING'
            ELSE 'INFO'
        END
    FROM performance_schema.events_statements_summary_by_digest
    WHERE SUM_CREATED_TMP_DISK_TABLES > 1000;
    -- Output the report
    SELECT 
        section,
        metric,
        value,
        severity
    FROM daily_report
    ORDER BY 
        CASE section
            WHEN 'Overall Statistics' THEN 1
            WHEN 'Top Offenders' THEN 2
            WHEN 'Resource Usage' THEN 3
            WHEN 'Recommendations' THEN 4
        END,
        CASE severity
            WHEN 'CRITICAL' THEN 1
            WHEN 'WARNING' THEN 2
            WHEN 'INFO' THEN 3
        END;
    -- Cleanup
    DROP TEMPORARY TABLE IF EXISTS daily_report;
END//
DELIMITER ;
-- Execute the report
CALL generate_daily_temp_report();

Script 50: Capacity Forecast Model



-- Predict future temp space needs based on historical growth
WITH daily_stats AS (
    SELECT 
        DATE(measurement_time) AS date,
        AVG(disk_temp_pct) AS avg_disk_pct,
        MAX(ibtmp1_size_mb) AS max_size_mb,
        AVG(ibtmp1_used_mb) AS avg_used_mb
    FROM temp_usage_history
    WHERE measurement_time >= DATE_SUB(NOW(), INTERVAL 30 DAY)
    GROUP BY DATE(measurement_time)
),
growth_rate AS (
    SELECT 
        AVG((max_size_mb - LAG(max_size_mb) OVER (ORDER BY date)) / NULLIF(LAG(max_size_mb) OVER (ORDER BY date), 0) * 100) AS daily_growth_pct,
        STDDEV((max_size_mb - LAG(max_size_mb) OVER (ORDER BY date)) / NULLIF(LAG(max_size_mb) OVER (ORDER BY date), 0) * 100) AS growth_volatility
    FROM daily_stats
)
SELECT 
    'Capacity Forecast' AS analysis,
    CONCAT(ROUND(daily_growth_pct, 2), '%') AS avg_daily_growth,
    CONCAT(ROUND(growth_volatility, 2), '%') AS growth_volatility,
    CONCAT(
        'Projected size in 30 days: ',
        ROUND((SELECT MAX(max_size_mb) FROM daily_stats) * POWER(1 + (daily_growth_pct/100), 30), 2),
        ' MB'
    ) AS forecast_30_days,
    CONCAT(
        'Projected size in 90 days: ',
        ROUND((SELECT MAX(max_size_mb) FROM daily_stats) * POWER(1 + (daily_growth_pct/100), 90), 2),
        ' MB'
    ) AS forecast_90_days,
    CASE 
        WHEN daily_growth_pct > 5 THEN 'CRITICAL: Investigate immediate optimization opportunities'
        WHEN daily_growth_pct > 2 THEN 'WARNING: Monitor closely and plan optimizations'
        ELSE 'INFO: Growth rate is manageable'
    END AS recommendation
FROM growth_rate;
