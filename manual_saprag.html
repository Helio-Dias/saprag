SAPRAG User Manual

A document chunking, semantic search, and answer-refinement toolkit.

Overview

SAPRAG is a knowledge pipeline that turns your documents into a searchable, AI-answerable knowledge base. It splits documents into overlapping chunks, computes vector embeddings for them, and answers questions with a multi-query Retrieval-Augmented Generation (RAG) pipeline backed by a local language model.

Everything is driven from a single central menu, saprag.py, which dispatches to the individual modules:

Menu optionWhat it does
Insert document (interactive chunking)Chunk one file and store it in PostgreSQL + Firestore
Process new filesBatch-ingest everything in arquivos_novos/ into Firestore
Compute embeddingsGenerate vector embeddings for chunks that don't have one yet
Search (RAG pipeline)Ask a question and get a sourced answer
Evolve cached answersRe-answer recent questions by reading full documents (no RAG)
Migrate PostgreSQL → FirestoreCopy existing documents/chunks from Postgres into Firestore
Primary store: GCP Firestore (helio-test-db). PostgreSQL is a secondary/local store used by the interactive chunker and the migration tool.

Launching SAPRAG

Start the central menu from the project directory:

python3 saprag.py

Use the arrow keys to move and Enter to select. Each action runs, then returns you to the menu. Errors in one action (for example a missing model or a database that's down) are caught and reported without crashing the menu, so you can fix the issue and try again.

Requires a real terminal. The menu uses simple-term-menu, which needs an interactive TTY. It won't run with piped input.

Document Ingestion

There are two ways to get documents into the knowledge base.

Option A — Interactive (one file)

Menu: Insert document (interactive chunking). Writes to both PostgreSQL and Firestore.

1

Choose file

Pick a .txt, .doc, .docx, or .md file from the current directory.
2

Choose description

A short human-readable label for the document.
3

Choose chunk size & overlap

Defaults: 528 characters per chunk, 128 characters of overlap. Overlap keeps context from being lost at chunk boundaries.
4

Run chunking

The file is read, split, and inserted as an atomic transaction in PostgreSQL plus a batch write to Firestore.

Option B — Batch (a folder of files)

Menu: Process new files. Processes everything in the arquivos_novos/ folder straight into Firestore.

  • Supported formats: .doc, .docx, .txt, .md, .pdf.
  • .doc/.docx Confluence exports are parsed from multipart MIME; HTML is stripped and validated.
  • .pdf text is extracted page by page.
  • Deduplicates by file path, so re-running won't create duplicates.
  • The description is auto-generated from the (URL-decoded) file name.
  • An ingestion date (data_onboard) is stored — used later to resolve contradictions by preferring the most recent document.

How chunking works

  • Text is split into pieces of chunk size characters with overlap between consecutive chunks.
  • If a cut would land in the middle of a word, it advances to the next whitespace boundary.
  • Chunking is deterministic — the same input always yields the same chunks, which makes a document fully reproducible from its source.

Searching

Menu: Search (RAG pipeline). Type a question and get an answer grounded in your documents. The answer is always returned in the same language as your question.

How the pipeline works

0

Cache check

The question is embedded and compared against previously answered questions. A close enough match returns instantly (see Cache Benefits).
1

Decomposition

Claude Haiku breaks your question into 2–4 focused sub-queries, each keeping the central context of the original.
2

Multi-query search

All chunks are loaded once; the original query and every sub-query are matched by cosine similarity, then merged and de-duplicated by best score.
3

Round 1 synthesis

The model answers from the retrieved chunks and, if anything is incomplete or truncated, generates follow-up questions.
4

Round 2 (automatic)

If follow-ups exist, a second search gathers new chunks and a final consolidated answer is produced.

Tuning parameters

ConstantDefaultMeaning
TOP_K_PER_QUERY5Chunks returned per sub-query
TOP_K_MERGED15Max chunks in round 1 after dedup
TOP_K_SECOND_ROUND10Max new chunks in round 2
MAX_SUB_QUERIES4Limit of generated sub-queries
Contradiction resolution: when chunks disagree, the most recently onboarded document wins. If dates are equal, the majority of chunks is followed.

Cache Benefits

Every completed answer is saved to a result cache along with the question's embedding. Before running the full (and relatively expensive) pipeline, SAPRAG compares a new question to cached ones by cosine similarity and acts on how close the match is.

Match levelSimilarityBehavior
Perfect≥ 0.98Returns the cached answer directly
Near-perfect≥ 0.92Returns the cached answer directly
Auxiliary≥ 0.85Feeds the cached answer in as extra context during synthesis
Miss< 0.85Runs the full pipeline

Why it matters

  • Speed: repeated or near-identical questions skip the model entirely and return in a fraction of a second.
  • Cost: fewer embedding and generation calls.
  • Consistency: the same question gives the same answer rather than re-deriving it each time.
  • Partial reuse: even a loose match (auxiliary) helps — the old answer becomes additional context for a fresh synthesis.
Note: the cache is a semantic de-duplicator, not a search log. A repeated question updates usage counters on the existing cache entry rather than creating a new record.

Evolution

Menu: Evolve cached answers. Evolution tries to produce answers that are better than what the RAG pipeline already cached.

The idea: a RAG answer can lose context because it only sees a handful of generic chunks. Evolution instead reads the entire documents, whole, with Claude Haiku — no vector search — to re-answer recent cached questions more completely.

Running it

You are asked for two numbers:

PromptMeaning
Minute budget (total)Total time to spend this run
Number of cached questionsThe N most recent cached questions to improve

The budget is split evenly. Example: 10 minutes over 5 questions = 2 minutes each for the 5 most recent cached questions.

How it works (map-reduce, no RAG)

1

Map

For each stored document, its chunks are joined into full text and the model extracts only what's relevant to the question.
2

Reduce

Once every document has been read, the collected evidence is synthesized into a final answer, explicitly aiming to surpass the cached one while staying grounded in the evidence.

Key behaviors

  • Soft deadline: the per-question time slice is checked before reading each document. A model call already running is allowed to finish, so wall time can slightly exceed the slice.
  • Resumable: reading the whole corpus is slow (each map step is a CLI call to Haiku) and rarely finishes in one slice. Progress (next document + evidence so far) is persisted. Re-run with the same count to continue; the final answer is written only after the whole corpus has been read.
  • Model load not charged: the model is loaded once before the per-question clocks start.
Expect multiple runs. Each map step is a separate CLI call to Haiku, so a large document set may not be fully read in one short budget. That is exactly why evolution is resumable — just run it again to pick up where it left off.

End-to-End Flow

A typical path from raw files to answers, all from the central menu:

  1. Copy files into arquivos_novos/.
  2. Process new files — chunk and store in Firestore.
  3. Compute embeddings — make the chunks searchable.
  4. Search — ask questions and get sourced answers.
  5. Evolve cached answers (optional) — improve the best answers offline over time.

Equivalent command-line invocation without the menu:

python3 process_new_files.py
python3 embed_chunks.py
python3 search.py "your question here"
